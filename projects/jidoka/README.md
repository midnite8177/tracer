# jidoka

The tool that replaces tracer. See [GLOSSARY.md](GLOSSARY.md) for its
words and [docs/adr/](docs/adr/) for its decisions.

## What you need

Python 3.10 or newer, with `git`, `bd` and `claude` on the PATH. `codex` is
optional; when it is on the PATH, the installer installs into Codex too.
There are no packages to install, and the installer installs none of the
tools above.

## Build and test

```bash
python3 projects/jidoka/install.py --config-dir <path> [--config-dir <path> ...]   # install, or update when run again
python3 projects/jidoka/release.py --bump patch                                    # or minor, major; or --version X.Y.Z
python3 projects/jidoka/untracer.py --repo <path>                                  # backups go to ~/.jidoka
sh projects/jidoka/plugin/jidoka/bin/jidoka-run <script.py> [args...]              # how hooks and skills reach Python
sh projects/jidoka/plugin/jidoka/bin/jidoka-run projects/jidoka/plugin/jidoka/scripts/repo_settings.py show   # the settings of the repo you are in
python3 projects/jidoka/tests/run_suite.py                                         # all tests, from the repo root
python3 projects/jidoka/tests/run_suite.py -k <part of a test's dotted name>       # only the tests it matches; repeat -k for more
```

`install.py`, `release.py` and `untracer.py` take `--jidoka-home` to use a
folder other than `~/.jidoka`, and the launcher reads `JIDOKA_HOME`. Install
refuses while `plugin/` has an uncommitted change, so commit first. It then
writes the committed `plugin/` to `<jidoka-home>/plugins/<version>/` with
`git archive` and adds that snapshot as the marketplace, so editing `plugin/`
never changes the scripts under a running session. A snapshot is never
rewritten. Install reuses one that came from the same plugin content, and
refuses when the version's snapshot came from different content, so run
`release.py` to give a change a new version. Old snapshots stay. To try the
installer without touching your own config, point `--config-dir` at an empty
folder and set `CODEX_HOME` to another.

The tests run each script as a process against a temporary git repo that
holds copies of the scripts and the plugin folder, a temporary jidoka home,
and a fake `bd`, `tests/fake_bd.py`, first on the PATH. The fake keeps its
beads in a JSON file in the repo's `.beads/`, because each call of real bd
opens its database and takes a second or more. It answers only the calls
the scripts and their tests make, and fails on any other.
`tests/test_fake_bd.py` runs those calls against real bd and the fake and
compares what they print. Real bd still runs where a test needs what it
writes: the stealth script's tests, the installer's stealth workspace test
and the onboarding test that switches a repo to stealth. The `claude` and
`codex` they find are small fakes that record their arguments. The fake
`codex` also keeps its marketplaces in a file, and refuses to add one it
already has from a different source, as Codex does. The Python version check is
the one test that calls a function, because no process can run under an
older Python.

Each stealth beads workspace is a copy of one that `bd init --stealth` made
once, because bd init takes seconds and a copy does not. Every copy keeps
that workspace's bead id prefix. `run_suite.py` runs the test classes side
by side, one class at a time in each of up to `os.cpu_count()` worker
processes, so a class's `setUpClass` still holds for all of its tests. The
first worker that needs the workspace makes it, and the others copy from
it. The runner prints unittest's summary and exits as unittest does: 0
when all pass, 1 when one fails, 5 when no test ran. `python3 -m unittest discover -s projects/jidoka/tests` still runs
the same tests one at a time, and makes the workspace once in its process.

## Where things are

| `install.py` | Checks the tools, records the Python, config dirs, routes and jidoka's source repo in `<jidoka-home>`, writes the committed plugin to `<jidoka-home>/plugins/<version>/`, and installs that snapshot into each named config dir and into Codex. Running it again updates. The source repo is the main worktree of the checkout it runs from, and retro files fixes to jidoka there |
| `release.py` | Raises the plugin version and makes the one commit that holds it |
| `plugin/` | The local marketplace, committed in git. `plugin/jidoka/` is the plugin: its manifest and `bin/jidoka-run`, the launcher |
| `plugin/jidoka/hooks/` | `hooks.json` wires the SessionStart hook and names `lap_mod.ts`, the lap mod. At `agent.spawn` the lap mod reads a first prompt line `jidoka lap worktree: <absolute path>`, runs the worker in that worktree, and keeps the worker's id, worktree and commands in `$.state`, the commands being each app's `test` and the `worker_commands` that `repo_settings.py show` prints there. At `tool.check` it allows a lap worker's read-only calls, its writes inside the worktree and Bash commands whose every part starts with the words of one of those commands. It denies, with a reason, a write outside the worktree, a command holding `$(`, a backtick or a `>`, an `Agent` or `Workflow` call, and every other call. `ToolSearch`, `SendMessage`, `ListAgents`, `AskUserQuestion` and `SubagentHandback`, which delivers a background worker's report, go on to the host. It allows the host's Bash calls that run the launcher on a script inside the plugin, and leaves every other host call, and every subagent that is not a lap worker, to the host. `lap_mod.test.ts` holds its tests, which `claude plugin test` runs. `types/index.d.ts` declares the `$.state` value it keeps. In `hooks/`, `session_start.py` prints the rules block and the doc paths in a repo that has beads, and nothing elsewhere. In a beads repo with no repo settings it adds one line saying to run `/jidoka:onboard`. Its commit rule says the glossary and ADRs are always committed, or, when the repo settings keep them private, that they stay uncommitted in that repo, naming their paths. After the rules it lists each rule conflict the repo settings record, the repo's rule winning over the jidoka rule it quotes, and prints no list when there are none or they cannot be read |
| `plugin/jidoka/scripts/` | `repo_settings.py` writes a repo's settings to `<jidoka-home>/repos/<name>-<hash>.json`, keyed by the path of its main worktree, and shows them from any worktree. It refuses settings in which no app has a build or no app has a test command, an app whose `test` or `test_target` is null while its other test settings are not empty, and a hand-run group without a name, exclusion, command or reason, or whose exclusion is missing from the app's full-suite command or from its targeted command, `test` followed by `test_target`. An app with no test command has null for `test`, `test_target` and `test_full`, and `[]` for `hand_run`. An app's `acceptance` is the folder of its acceptance specs inside the repo, or null; an app that leaves it out has none. It derives the full suite from each app's `test` followed by its `test_full`, leaving out the apps with no test command, which it lists under `untested_apps`, and appends nothing to a command. It removes from the main worktree's `CLAUDE.local.md` the lines onboarding moved into the settings. It records the `glossary` and `adrs` paths, `GLOSSARY.md` and `docs/adr` when not given, and `glossary_and_adrs`, `committed` or `private`, `committed` when not given; a rerun that leaves them out keeps the stored values. It records `rule_conflicts`, `[]` when not given, each with the repo's rule, the repo path of the file it is written in and the jidoka rule it overrules, and refuses every entry without one of those at once; a rerun that leaves the list out keeps it, and one that gives it replaces it. Private adds one anchored line per path to the repo's `info/exclude` and refuses while git tracks either path; going back to committed, or moving a private path, takes out the lines it added and keeps every other byte. It refuses to write while git tracks the main worktree's `.beads/`, and names the command that runs `beads_stealth.py`. `beads_stealth.py` puts the main worktree's beads workspace in stealth mode. With no `.beads/` it runs `bd init --stealth --non-interactive`. With a tracked one it untracks `.beads/` and `.agents/skills/beads/` with `git rm -r --cached`, and also `.claude/settings.json`, `.codex/hooks.json` and `.codex/config.toml` when they hold nothing but what bd writes; it names a hook file that holds more and leaves it committed. It takes bd's marked blocks out of `CLAUDE.md` and `AGENTS.md` and stages the edit, or untracks the file whole when only bd's stock text is left. A block whose BEGIN line is gone runs from the last `## Beads Issue Tracker` heading above its END line; with no such heading the file stays as it is, and the script names it as still committed with bd's blocks. It adds a line to the repo's `info/exclude` for each path it untracks and leaves its changes staged, never committed, so the files and every bead stay on disk. `git_exclude.py` adds lines to the repo's `info/exclude` once and takes them out again, keeping every other byte, for the stealth, settings and bench scripts. It builds the line that hides one path at the repo root: `/<path>/` for a folder, such as `.agents/skills/beads`, and `/<path>` for a file. The ADR folder's line is `/<path>` too, so it also hides the link a bench worktree holds there; the settings script takes out the slashed form. The workspace's `.beads/` and bench's `.worktrees/` stay unanchored, the form bd init and bench write. `bd_files.py` holds the stock text and hook files plain `bd init` writes, which decide what counts as bd's alone. The script refuses, naming the paths, while the index holds staged changes to other files, or while a rules file it edits has unstaged changes. In a clone that pulled the commit holding the switch, it writes back the files that commit untracked, from the commit before it, only where they are missing on disk, and excludes them. A run with nothing to do changes nothing, and the repo's `.gitignore` and `core.hooksPath` stay as they are. `land.py` puts a bead's branch on local main as one commit. It takes the merge lock at `<jidoka-home>/locks/merge.lock`, which the merge gate shares, refuses a bead whose recorded targeted tests did not pass, rebases the branch on main, prints a line that names each app in `untested_apps` as having no tests, then runs every command of the repo settings' `full_suite` there, fast-forwards main in the checkout that has it, closes the bead and removes the worktree and branch. After exit 0, 4 or 5 it lists each app's hand-run tests with the reason and the command that runs them. It exits 3, naming the files, while uncommitted edits in main's checkout touch files the bead changed, and 4 when main has the commit but a closing step failed; running it again repeats those steps. It exits 5 when the full suite failed, naming each failing command with its output, and main is unchanged. It refuses a repo with no repo settings, or settings with no `hand_run` or `untested_apps` list, with 1. `commands.py` holds the git, bd and test command runners the scripts call. A git or bd runner takes the environment to run in, or None for the caller's. It also holds the lookups the scripts share: a ref's commit, the worktree list, `bd show` of one bead, the environment that sets `BEADS_ACTOR` to the repo's `git config user.name`, and the one that sets it to `jidoka` for what the factory writes on a lap. `bench.py` starts, ends and releases bench work and prints a tier's route. `start` refuses an epic, a task whose epic carries the `factory` label, a bead someone else has claimed, and a repo with no `git config user.name`. It makes or reuses the bead's worktree at `.worktrees/<slug>` in the main checkout, on the branch `bench/<slug>` cut from main, and then claims the bead under that name whatever `BEADS_ACTOR` says, so a failed worktree step leaves the bead unclaimed. It adds `.worktrees/` to the repo's `info/exclude` once. When the repo settings keep the glossary and ADRs private, `private_docs.py` gives the worktree a link at each of their paths to the main checkout's copy, so every worktree shares one copy, and start refuses before the claim, naming the path, when the worktree holds its own file or folder there. It records the branch, worktree and start sha in the bead's `bench.*` metadata, and posts `bench started at <sha> on <branch>`. `end` posts the outcome, `release` sets the bead open with no assignee and leaves the worktree, branch and commits, and `route <tier>` prints the tier's route from `<jidoka-home>/settings.json` or refuses, saying to run the installer. `targeted_tests.py` runs an app's test command with the given filter in its `test_target`, once, in a bead's worktree after merging the `--base` branch into it, main at the bench, or with `--rebase` after rebasing the worktree's branch onto it, the epic branch on a lap, so the epic branch stays one commit per task. When that branch moved during the run it brings it in again and reruns once. It sets `tests.command`, `tests.base` and `tests.result`, which `land.py` and the merge gate read, then posts the exact command, the result, the base branch and its sha as a comment on the bead. It exits 3 when the tests failed. Without recording anything, it exits 4 when the filter starts with the text the `test_target` puts before its placeholder, or when the run's output shows it executed no tests; in that second case it names the app's hand-run tests, which the `test_target` leaves out. It exits 1 on a merge or rebase conflict, a base branch that does not exist, or when the repo settings lack the app or a placeholder, and when the app's settings are incomplete or lack `untested_apps` it points at `/jidoka:onboard`. It exits 1 for an app with no test command before merging main, saying to build a test project for it at the bench and then run `/jidoka:onboard` to record its command. `merge_gate.py` is the merge gate. Under the merge lock it merges a lap into the epic branch only when the latest targeted run recorded on the task passed on the epic branch's current head, the lap's head contains that head and has a commit the epic branch lacks, the lap changed no protected path, and the main checkout does not have the epic branch checked out with uncommitted edits. It fast-forwards the epic branch with `git update-ref` and an old-value check, brings the main checkout's files along when it has the epic branch checked out, then, under the actor `jidoka`, closes the task with the commit's sha in the reason, sets `lap.stage=merged`, and removes the lap's worktree and branch. The scheduler calls it, and `merge_gate.py <task>` runs it alone: it exits 1 naming the failed check, 3 when the epic branch moved since the run, and 4 when the epic branch has the commit but a closing step failed. `handoff.py` gives an epic to the factory. `check <epic>` makes the handoff checks and prints the epic branch's name and the epic's tasks, its children that are not closed, each with its Seams section. It writes nothing and lists every failure with its fix when the epic or one of its tasks waits on an open bead outside the epic, the epic holds an epic or no tasks, the repo has no repo settings, an app is in `untested_apps` or there is no full suite, a holdout names a task outside the epic, the epic carries the `factory` label, or an app with holdouts or an `acceptance` folder has a null `way_in`. It also refuses a title with no letters or digits, and an `epic/<slug>` branch that exists and that the epic does not record. `take <epic> --area <task>=<area> ...` makes the same checks, refuses a task with no area and an area for a bead that is not one of the epic's tasks, then, under the git user's name, sets `lap.track=simple` and `lap.area` on each task, records the branch as the epic's `factory.branch`, cuts `epic/<slug>` from main, posts one comment holding the task table, and adds the `factory` label last. A rerun reuses the branch the epic records and posts no second table. It starts nothing. `holdouts.py` reads and writes an epic's holdouts, each an app and the tasks it exercises, as zlib-compressed, base64-encoded JSON under the epic's `holdouts` metadata; `write <epic>` stores the JSON list on stdin. `factory.py check` tells whether this session can run the factory, and lists every failure at once. The plugin it sits in, which the session loaded at startup, must name `./lap_mod.ts` in `hooks/hooks.json`'s modules and hold that file; otherwise it says to start a new session. `claude plugin list --json`, run in the caller's environment, must show a plugin whose id starts with `jidoka@` enabled in the host's config dir, `$CLAUDE_CONFIG_DIR` or else `~/.claude`; otherwise it names that dir and says to run `install.py --config-dir` on it. It exits 0 with one line, and 1 with the reasons on stderr |
| `plugin/jidoka/scripts/scheduler.py` | The scheduler. `next <epic>` makes handoff's checks again, except that the epic must carry the `factory` label and record an epic branch that exists, and an epic whose tasks are all closed passes; it lists every failure at once and writes nothing. Then it opens a lap for each ready task, in bd priority order and then by id, up to the repo settings' `lap_limit` and never two in one area. A ready task waits on no open bead, and has no open lap, no assignee and no `human` label. A lap gets the worktree `.worktrees/lap-<task>` on the branch `lap/<task>` cut from the epic branch, the lowest slot no open lap of the epic holds, and the scratch folder `.scratch` in its worktree, which a line of the repo's `info/exclude` hides. Under the actor `jidoka`, the task goes to in_progress with the assignee `jidoka`, and its metadata gets `lap.number`, `lap.stage`, `lap.tries`, `lap.workspace`, `lap.slot` and `lap.branch`. It prints the build actions and every open lap as one JSON object. A later call reads the open laps back from that metadata, and a rerun reuses a worktree and branch it finds. `report <epic> <task> <outcome>` takes how a lap's build ended: `done` with `--app` and `--filter`, `failed`, or `cut off`. On done it first stages everything the build left in the lap's worktree, puts the scratch folder back out of the index, and commits the rest as one commit whose message is the task's title, under the repo's git user; a build that left no changes makes no commit. Then it runs the targeted tests on the lap's head merged with the epic branch and, when they pass, the merge gate, and runs the tests again when the gate finds the epic branch moved. A failed build, a red run, a refused filter and a lap the gate finds with no commit of its own each count a try in `lap.tries` and send the lap back to the build; `cut off` sends it back without a try. The third try, a conflict merging the epic branch into the lap, and any other refusal of the gate park the task: `lap.stage=parked`, status open, no assignee, the `human` label and a comment saying why, with the worktree and branch kept. A parked lap holds no slot or area. Then it does what `next` does and prints the same JSON object, its actions led by the lap sent back |
