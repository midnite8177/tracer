# jidoka

The tool that replaces tracer. See [GLOSSARY.md](GLOSSARY.md) for its
words and [docs/adr/](docs/adr/) for its decisions.

## What you need

Python 3.10 or newer, with `git`, `bd` and `claude` on the PATH. `codex` is
optional; when it is on the PATH, the installer installs into Codex too.
`dotnet`, the .NET 10 SDK, is optional too; when it is on the PATH, the
installer publishes jidoka-ui so that `/jidoka:factory` can start it.
There are no packages to install, and the installer installs none of the
tools above.

## Build and test

```bash
python3 projects/jidoka/install.py --config-dir <path> [--config-dir <path> ...]   # install, or update when run again
python3 projects/jidoka/release.py --bump patch                                    # or minor, major; or --version X.Y.Z
python3 projects/jidoka/untracer.py --repo <path>                                  # backups go to ~/.jidoka
sh projects/jidoka/plugin/jidoka/bin/jidoka-run <script.py> [args...]              # how hooks and skills reach Python
sh projects/jidoka/plugin/jidoka/bin/jidoka-run projects/jidoka/plugin/jidoka/scripts/repo_settings.py show   # the settings of the repo you are in
python3 projects/jidoka/tests/run_suite.py                                         # all tests, from the repo root
python3 projects/jidoka/tests/run_suite.py -k <part of a test's dotted name>       # only the tests it matches; repeat -k for more
```

`install.py`, `release.py` and `untracer.py` take `--jidoka-home` to use a
folder other than `~/.jidoka`, and the launcher reads `JIDOKA_HOME`. Install
refuses while `plugin/` has an uncommitted change, so commit first. It then
writes the committed `plugin/` to `<jidoka-home>/plugins/<version>/` with
`git archive` and adds that snapshot as the marketplace, so editing `plugin/`
never changes the scripts under a running session. A snapshot is never
rewritten. Install reuses one that came from the same plugin content, and
refuses when the version's snapshot came from different content, so run
`release.py` to give a change a new version. Old snapshots stay. To try the
installer without touching your own config, point `--config-dir` at an empty
folder and set `CODEX_HOME` to another.

The tests run each script as a process against a temporary git repo that
holds copies of the scripts and the plugin folder, a temporary jidoka home,
and a fake `bd`, `tests/fake_bd.py`, first on the PATH. The fake keeps its
beads in a JSON file in the repo's `.beads/`, because each call of real bd
opens its database and takes a second or more. It answers only the calls
the scripts and their tests make, and fails on any other.
`tests/test_fake_bd.py` runs those calls against real bd and the fake and
compares what they print. Real bd still runs where a test needs what it
writes. These are the stealth script's tests, the installer's stealth
workspace test, the onboarding test that switches a repo to stealth, and the
test in `tests/test_jidoka_fixture.py`, which checks the workspace copied from
the one bd init made. Three classes in `tests/test_untracer.py` also use real
bd. `BdWrittenRemovalTests` and `BdWrittenRulesPlacementTests` check that
untracer leaves bd's hooks, marked block, `info/exclude` heading and
workspace as bd wrote them. `CommittedRulesTests` checks that a committed
`CLAUDE.md` keeps the text bd wrote. The `claude` and
`codex` they find are small fakes that record their arguments. The fake
`codex` also keeps its marketplaces in a file, and refuses to add one it
already has from a different source, as Codex does. The Python version check is
the one test that calls a function, because no process can run under an
older Python.

Each stealth beads workspace is a copy of one that `bd init --stealth` made
once, because bd init takes seconds and a copy does not. Every copy keeps
that workspace's bead id prefix. `run_suite.py` runs the test classes side
by side, one class at a time in each of up to `os.cpu_count()` worker
processes (at most 61 on Windows, where a process pool allows no more), so a class's `setUpClass` still holds for all of its tests. The
first worker that needs the workspace makes it, and the others copy from
it. The runner prints unittest's summary and exits as unittest does: 0
when all pass, 1 when one fails, 5 when no test ran. `python3 -m unittest discover -s projects/jidoka/tests` still runs
the same tests one at a time, and makes the workspace once in its process.
