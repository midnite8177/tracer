# jidoka

The tool that replaces tracer. See [GLOSSARY.md](GLOSSARY.md) for its
words and [docs/adr/](docs/adr/) for its decisions.

## What you need

Python 3.10 or newer, with `git`, `bd` and `claude` on the PATH. `codex` is
optional; when it is on the PATH, the installer installs into Codex too.
There are no packages to install, and the installer installs none of the
tools above.

## Build and test

```bash
python3 projects/jidoka/install.py --config-dir <path> [--config-dir <path> ...]   # install, or update when run again
python3 projects/jidoka/release.py --bump patch                                    # or minor, major; or --version X.Y.Z
python3 projects/jidoka/untracer.py --repo <path>                                  # backups go to ~/.jidoka
sh projects/jidoka/plugin/jidoka/bin/jidoka-run <script.py> [args...]              # how hooks and skills reach Python
sh projects/jidoka/plugin/jidoka/bin/jidoka-run projects/jidoka/plugin/jidoka/scripts/repo_settings.py show   # the settings of the repo you are in
python3 projects/jidoka/tests/run_suite.py                                         # all tests, from the repo root
python3 projects/jidoka/tests/run_suite.py -k <part of a test's dotted name>       # only the tests it matches; repeat -k for more
```

`install.py`, `release.py` and `untracer.py` take `--jidoka-home` to use a
folder other than `~/.jidoka`, and the launcher reads `JIDOKA_HOME`. Install
refuses while `plugin/` has an uncommitted change, so commit first. It then
writes the committed `plugin/` to `<jidoka-home>/plugins/<version>/` with
`git archive` and adds that snapshot as the marketplace, so editing `plugin/`
never changes the scripts under a running session. A snapshot is never
rewritten. Install reuses one that came from the same plugin content, and
refuses when the version's snapshot came from different content, so run
`release.py` to give a change a new version. Old snapshots stay. To try the
installer without touching your own config, point `--config-dir` at an empty
folder and set `CODEX_HOME` to another.

The tests run each script as a process against a temporary git repo that
holds copies of the scripts and the plugin folder, a temporary jidoka home,
and a fake `bd`, `tests/fake_bd.py`, first on the PATH. The fake keeps its
beads in a JSON file in the repo's `.beads/`, because each call of real bd
opens its database and takes a second or more. It answers only the calls
the scripts and their tests make, and fails on any other.
`tests/test_fake_bd.py` runs those calls against real bd and the fake and
compares what they print. Real bd still runs where a test needs what it
writes. These are the stealth script's tests, the installer's stealth
workspace test, the onboarding test that switches a repo to stealth, and the
test in `tests/test_jidoka_fixture.py`, which checks the workspace copied from
the one bd init made. Three classes in `tests/test_untracer.py` also use real
bd. `BdWrittenRemovalTests` and `BdWrittenRulesPlacementTests` check that
untracer leaves bd's hooks, marked block, `info/exclude` heading and
workspace as bd wrote them. `CommittedRulesTests` checks that a committed
`CLAUDE.md` keeps the text bd wrote. The `claude` and
`codex` they find are small fakes that record their arguments. The fake
`codex` also keeps its marketplaces in a file, and refuses to add one it
already has from a different source, as Codex does. The Python version check is
the one test that calls a function, because no process can run under an
older Python.

Each stealth beads workspace is a copy of one that `bd init --stealth` made
once, because bd init takes seconds and a copy does not. Every copy keeps
that workspace's bead id prefix. `run_suite.py` runs the test classes side
by side, one class at a time in each of up to `os.cpu_count()` worker
processes, so a class's `setUpClass` still holds for all of its tests. The
first worker that needs the workspace makes it, and the others copy from
it. The runner prints unittest's summary and exits as unittest does: 0
when all pass, 1 when one fails, 5 when no test ran. `python3 -m unittest discover -s projects/jidoka/tests` still runs
the same tests one at a time, and makes the workspace once in its process.

At a terminal it asks for the Pushover user key, application token and jidoka-ui address, and writes them to `<jidoka-home>/pushover.json` for its owner only; the keys never pass through a model |
| `release.py` | Raises the plugin version and makes the one commit that holds it |

It starts nothing. `epic_reader.py` reads an epic, its children and its tasks from bd, raising `EpicReadError` when bd prints what it cannot read, and holds the checks that stay true while the factory holds the epic (a wait on an open bead outside it, a nested epic, missing repo settings, holdouts that name a bead outside it, an app with no way in), which `handoff.py` and `scheduler.py` both run, each with its own wording for the advice to run again. `holdouts.py` reads and writes an epic's holdouts, each an app, the tasks it exercises and its scenario, as zlib-compressed, base64-encoded JSON under the epic's `holdouts` metadata; `write <epic>` stores the JSON list on stdin in place of any held and refuses a holdout that names no task, `read <epic>` prints the list, `[]` when the epic has none, `read <epic> --task <task>` prints only the holdouts that name the task, each with its `holdout` number among all of them, and `brief <epic>` prints the epic's id, title and spec, and each app's name, way in and acceptance folder, with no task and no write. `factory.py check` tells whether this session can run the factory, and lists every failure at once. | `plugin/jidoka/scripts/scheduler.py` | The scheduler. `next <epic>` makes handoff's checks again, except that the epic must carry the `factory` label and record an epic branch that exists, and an epic whose tasks are all closed passes; it lists every failure at once and writes nothing. Then it opens a lap for each ready task, in bd priority order and then by id, up to the repo settings' `lap_limit` and never two in one area. A ready task waits on no open bead, and has no open lap, no assignee and no `human` label. A lap gets the worktree `.worktrees/lap-<task>` on the branch `lap/<task>` cut from the epic branch, the lowest slot no open lap of the epic holds, and the scratch folder `.scratch` in its worktree, which a line of the repo's `info/exclude` hides. Under the actor `jidoka`, the task goes to in_progress with the assignee `jidoka`, and its metadata gets `lap.number`, `lap.stage`, `lap.tries`, `lap.workspace`, `lap.slot` and `lap.branch`. It prints the build actions and every open lap as one JSON object. A later call reads the open laps back from that metadata, and a rerun reuses a worktree and branch it finds. `report <epic> <task> <outcome>` takes how a lap's build ended: `done` with `--app` and `--filter`, `failed`, or `cut off`. On done it first stages everything the build left in the lap's worktree, puts the scratch folder back out of the index, and commits the rest as one commit whose message is the task's title, under the repo's git user; a build that left no changes makes no commit. Then it runs the targeted tests on the lap's head merged with the epic branch and, when they pass, the merge gate, and runs the tests again when the gate finds the epic branch moved. A failed build, a red run, a refused filter and a lap the gate finds with no commit of its own each count a try in `lap.tries` and send the lap back to the build; `cut off` sends it back without a try. `question` takes a worker's question report, `question.json` in the lap's scratch folder, and `park.py` posts it on the task as a `Question:` comment holding what the worker found, each option with its confidence in percent and the recommended one, sets `question.options` and `question.recommended` in the task's metadata, and parks the task as below; a missing or unusable report counts a try instead. The human answers by taking the `human` label off: the task is ready again, and the build action of its new lap carries `answer`, which is every comment anyone but `jidoka` posted since the `Question:` comment (`source` `comment`), or the recommended option when there are none (`source` `recommendation`), and is null when the task's last park was not a question. The new lap reuses the worktree and branch with their commits; a comment that asks back is replied to by the build with a new question report, which parks the task again. The lap mod denies a lap worker `AskUserQuestion`. A conflict rebasing the lap onto the epic branch, or targeted tests that fail once that rebase brought in newer work, call the merge worker and count no try: the lap goes to `lap.stage=merge`, with `lap.mergewhy` and `lap.mergebase` (the epic branch's head) in the task's metadata, and its action is a `merge` action carrying `reason`, for a worker on the deep tier. The merge worker rebases the lap onto the epic branch in its worktree, resolves the conflicts and fixes what the merge broke, and ends with `done`, naming the app and the filter, or `failed`. A `failed` report takes `--why`, the worker's reason, which the try's comment and the park's carry; `--why` with any other outcome is refused. On `done` the scheduler folds what the worker left into the lap's own commit, so the epic branch keeps one commit per task, and runs the targeted tests and the merge gate again. A worktree left in the middle of a rebase, a lap head without `lap.mergebase`, red tests and a `failed` are each a merge try in `lap.mergetries`, and the second parks the task. `blocked` takes the discovered-work report, `discovered.json` in the lap's scratch folder, and ends the lap blocked on the new task it cannot finish without, as `discovered.py` describes; a `done` files the findings placed `epic` or `outside` first. The third build try and any other refusal of the gate park the task: `lap.stage=parked`, status open, no assignee, the `human` label and a comment saying why, with the worktree and branch kept. A parked lap holds no slot or area. A task whose `lap.track` metadata is `full` has a lap that runs a research brief (stage `research`, light tier), the build (deep tier), the targeted tests, the app check (stage `app-check`, standard tier, only when a holdout names the task) and the Spec check (stage `spec-check`, standard tier) in that order, and the merge gate only after a `pass`; a lap starts at the research only while its task holds no `research brief:` comment. The research worker leaves its brief in `research-brief.md` in the scratch folder and ends `done`, and the scheduler posts it on the task as a `research brief:` comment. A build's `done` records its app and filter and, once the targeted tests pass, sends the lap to the app check, or to the Spec check when no holdout names the task. The app check worker, started as `jidoka:app-check` and not as a lap worker, reads the holdouts that name the task, runs the app on the lap's slot, and leaves `app-check.json` in the scratch folder, one `{holdout, verdict, saw}` for each of them, and ends `done`. Every holdout green sends the lap to the Spec check. A red one sends the lap back to a new build, with no try, whose action carries `app_check`, the failed holdouts' numbers, verdicts and `saw` and never a step; it counts with the Spec check's send-backs, so the second send-back of the lap parks the task. A report that is missing, unusable or quotes a scenario is a try of the app check. The Spec check worker leaves its outcome block in `spec-check.json` in the scratch folder, and its report is `pass`, `send back` or `cannot judge`. A `send back` posts the findings on the task and sends the lap to a new build whose action carries them as `findings`, with no try, and the second send-back of a lap parks the task; a missing or unusable block is a try of the Spec check. A `cannot judge` parks the task with the block's reason and counts no try. A `pass` merges through the gate with the targeted run the lap holds, and runs the tests again only when the epic branch moved since. Then it does what `next` does and prints the same JSON object, its actions led by the lap sent back. `report-holdouts <epic>` takes the validation worker's report on the epic's holdouts and then does what `carry-on` does; `--ended failed|cut-off` (with `--why`, the worker's reason, for `failed`) counts a run of the worker instead, as `validation.tries` on the epic, and the third such run parks the epic with the `human` label and sends the `epic-parked` notification. Every call that prints a manager's next moves claims the epic's heartbeat for the session in `$JIDOKA_SESSION_ID`, as `heartbeat.py` describes. `stop <epic>` is the manager's call when the human tells the host to stop: it ends every open lap interrupted, with `lap.stage=interrupted`, status open, no assignee, an `Interrupted:` comment and the worktree and branch kept, counts no try, cutoff or cap, then sends the `factory-stopped` notification through `notify.py` and prints `{"epic", "interrupted"}`. An interrupted task is ready again with a new lap |
